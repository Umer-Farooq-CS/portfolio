# Portfolio agent guide

## Project overview

- This is Umer Farooq's personal portfolio, built with React 18, TypeScript, Vite 5, Tailwind CSS 4, React Router, Motion, and Vitest.
- The production target is GitHub Pages. Vite defaults to the `/portfolio/` base path; `VITE_BASE_PATH=/` is used for a user site or custom domain.
- The site is content-led and evidence-first: projects, measured results, runnable lab demos, and contact flows should remain the focus.

## Source map

- `src/pages/` contains route-level pages. `src/pages/Index.tsx` composes the homepage chapters. `src/pages/ProfileSelectorPage.tsx` is the root ("/") — it is not a homepage chapter.
- `src/components/home/` contains the homepage chapters; `src/components/kit/Primitives.tsx` owns shared presentation primitives. `src/components/kit/ProjectCard.tsx`, `SkillsSection.tsx`, and `ExperienceSection.tsx` are the profile-aware, reusable renderings of a project/skills/experience.
- `src/index.css` is the design-system source of truth for palette, typography, spacing, shape, and motion tokens.
- `src/data/` is the source of truth for portfolio copy and structured content. Schemas in `src/data/schema.ts` and tests enforce content validity.
- `src/data/profiles.ts` defines the three professional lenses (development/infrastructure/presales) — route path, hero copy, home-chapter order, skill priority, and detail-page section template per profile. `src/lib/profile.ts` resolves the active one (`useActiveProfile()`) and rewrites paths between lenses (`pathForProfile`); never hand-roll that logic in a component. A `ProjectItem`/`ExperienceItem` never gets a second, lens-specific record — a lens only adds an optional `lenses`/`lensEmphasis` override on the existing shared record (see `ProjectLensView` in `src/data/projects.ts`), enforced by a Zod `superRefine` that rejects a `techFocus`/`metricFocus` value not already present in that record's real fields. Adding a fourth profile means adding one entry to `PROFILES` — not a new route file or a new data shape.
- Routes live under one parametric `<Route path=":profile">` block in `src/App.tsx` (plus the legacy bare routes, which resolve their lens from `localStorage`/default) — not tripled per profile. `src/data/route-meta.json` is the source of truth for per-route metadata; a profile-prefixed inner page or project detail has no entry of its own and instead falls back to the bare route's entry via the prefix-fallback in `scripts/prerender-routes.mjs`'s `resolveMeta()` (canonicalizing to the bare URL) — only a profile's own home route gets a real JSON entry. New **static** routes must still be registered in `src/App.tsx`, `src/data/route-meta.json`, and `scripts/routes.mjs` (which also carries the profile path list, `PROFILE_ROUTE_PATHS`, asserted against `src/data/profiles.ts` in `src/test/profiles.test.ts` since a Node script can't import a TS module).
- `src/data/taxonomy.ts` and `src/lib/accent.ts` jointly define semantic domain colors. Keep those mappings synchronized.
- `src/assets/` contains source imagery. `src/assets/optimized/` and its manifest are generated by `npm run images`.
- `public/og-portfolio.png`, `public/sitemap.xml`, and the CV PDF are generated artifacts; use their package scripts when intentionally refreshing them.
- `dist/`, `.shots/`, and `node_modules/` are generated or external; never hand-edit them.

## Design rules

- Preserve the "Telemetry" visual language: wide display headings, compact mono labels and readouts, precise hairlines, restrained surfaces, and data-first hierarchy.
- Color must carry meaning. Add or change hues through semantic CSS variables in `src/index.css`, with separate vivid mark/fill values and contrast-safe text values for both light and dark themes.
- Preserve the palette legend: thermal orange = HPC/compute and primary actions; cryo cyan = quantum; neural violet = AI; systems green = systems and verified states; interface blue = full-stack/apps; award amber = recognition only.
- Do not scatter raw hex values or one-off arbitrary color utilities through components. Route domain color through `taxonomy.ts` and `accent.ts`; route reusable UI color through shared primitives.
- Keep primary calls to action thermal orange. Use secondary hues selectively for domains, chapter markers, headings, metrics, charts, validation states, and evidence—not for body copy or large decorative washes.
- Maintain keyboard focus, reduced-motion behavior, semantic heading order, and WCAG AA text contrast.
- Prefer existing components, icons, and assets. Do not add dependencies for styling that the current system can express.

## Scroll model

- Three different behaviours, and they are not interchangeable. `src/lib/useSmoothScroll.ts` gives every route except `/` weighted, eased scrolling on **pointer devices**. `src/lib/useSectionTravel.ts` gives `/` a scripted travel between its three screens, also pointer-only. **Touch is never intercepted** anywhere: the landing page gets CSS `scroll-snap` under `@media (pointer: coarse)` instead (`html.landing-snap` in `src/index.css`), and the chapter pages get nothing at all.
- Do not add section snapping to the chapter pages. It was tried and removed. Measured on `/development`, no chapter fits a viewport on any device: 1.02-1.89 screens at 1440x900, 1.28-2.38 at 1280x720, 1.64-3.87 on a phone. Snapping therefore has to either skip content or behave differently from one gesture to the next.
- A `position: sticky` element must never be a `scroll-snap-align` target. It re-snaps to its own moving box every frame and pins the scroll. The landing page uses a zero-height static `.snap-anchor` for the first stop for exactly this reason.
- `window.addEventListener("scroll", …)` stays banned. Both hooks resync by comparing the offset they last wrote against `window.scrollY`, which is also how an anchor jump or route change cancels an in-flight animation.
- Any per-frame scrolling must call `window.scrollTo({ top, behavior: "instant" })`. `src/index.css` sets `html { scroll-behavior: smooth }`, so a plain `window.scrollTo` starts a *browser* smooth scroll; calling it once per frame restarts that animation every frame and the page never advances at all. Measured: a rAF loop stepping 12px produced `[0,0,0,0,0,0,0,0]`. Naming the behaviour overrides the stylesheet for that call only and leaves anchor links smooth.
- If you add a guard that detects "someone else scrolled", it must skip its own write on the frame it is unsure, and require two consecutive frames before acting. A guard that writes every frame erases the divergence it is trying to observe, and a single-frame test with a tight threshold reads ordinary motion as interference. Both mistakes were made here, and the second one broke scrolling outright.
- `npm run check:scroll` drives a real browser over all of this (desktop plus two phone profiles) after a build. None of it is reachable from jsdom, so it is the only thing protecting the scroll model. Run it whenever you touch either hook.
- The visitor can turn eased scrolling off in the top bar (`src/lib/scroll-motion.tsx`, persisted). `prefers-reduced-motion` overrides the preference in both directions.

## Implementation conventions

- Use the `@/` alias for imports from `src/` and keep TypeScript strict.
- Preserve lazy-loaded routes and below-the-fold modules unless a change specifically requires altering the loading boundary.
- Keep content edits in `src/data/` rather than embedding portfolio facts in page components.
- Preserve the GitHub Pages base-path behavior in `vite.config.ts`; deep links must continue to load under `/portfolio/`.
- Do not edit unrelated user changes or generated files incidentally.
- `npm run build` refreshes the tracked sitemap date. Review that diff and do not keep an unrelated date-only change.
- Do not deploy the site or refresh external/live data unless the task explicitly requests it.

## Parallel-agent policy

- For complex work that divides cleanly, use up to three parallel subagents for bounded, independent audits or implementation areas.
- Give each subagent non-overlapping ownership and an explicit deliverable. Do not delegate tightly coupled files or let multiple agents edit the same component or token source.
- The primary agent owns integration, reviews every combined change, resolves conflicts, and runs final validation.

## Validation

- Run `npm run verify` for lint, strict type-checking, and the Vitest suite.
- Run `npm run build` for the production bundle.
- Run `npm run build:gh-pages` when validating the complete GitHub Pages artifact, including prerendered routes and the SPA fallback.
- When browser-based visual QA is explicitly requested, run `npm run shots`; it captures desktop/mobile light/dark routes and includes the axe accessibility gate.
